2. **Implementation:**
   - **Application:**
     - `Account.DeleteAccount.DeleteMyAccountCommand` (no body) + handler.
     - Handler order: write `AccountDeleted` audit first (so the row's `UserId` references the still-existing account); then explicitly remove child rows for `Todos`, `RefreshTokens`, `UserRoles`, `PasswordResetTokens`; then remove the `User`. The explicit removal mirrors the relational cascade so the InMemory provider used in tests behaves the same as SQL Server (the InMemory provider does not enforce FK cascades; the relational migrations do).
   - **Api:** `AccountController.DeleteMyAccount` (`DELETE /api/account`) routes to the command. Returns 204.
   - The `SecurityAuditEvents` table has no FK to `Users`, so the audit row survives the user delete and remains queryable for compliance / forensics.
