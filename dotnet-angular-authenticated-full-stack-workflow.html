App Delivery Workflow

Audience: Claude agent only. This document is the single source of truth for what to do next. Do not rewrite it for human readability.

Mission: Drive ./docs/idea.md to a deployed app using this fixed, evaluable, parallelizable workflow.

Loop command: /loop 1m ./dotnet-angular-authenticated-full-stack-workflow.html ./docs/idea.md

Agent Protocol (run this every loop iteration)

Multi-agent coordination: Two or more agents may be running this workflow on different machines. dotnet-angular-authenticated-full-stack-workflow.html in origin/main is the shared lock table. Every status or owner change MUST be committed and pushed immediately so the other agent sees it on its next iteration. Identify yourself with a stable, unique data-owner value — for example claude@<hostname>. Never use the bare value claude when more than one agent is active.

  1. Sync from remote first. Run git fetch origin then git pull --rebase origin main in the repo root. Do not read dotnet-angular-authenticated-full-stack-workflow.html until the pull succeeds. If the working tree is dirty (uncommitted edits from a prior aborted iteration), git stash them, pull, then git stash pop and resolve before continuing.
  2. Read this file and parse every <article data-task-id="..."> element.
  3. Resolve statuses: for any task whose data-status="blocked", recheck dependencies. If every ID in data-depends-on has data-status="done" (or the list is empty), update that task's data-status to ready. If you flipped any statuses, save, commit (chore(workflow): unblock <ids>), and push before continuing.
  4. Pick the next task using this priority order:
    1. Any task already data-status="in-progress" with data-owner equal to your identifier — resume it.
    2. Otherwise, the first task in document order with data-status="ready" and data-owner="".
    3. If no ready task exists and any task is still blocked or in-progress by another owner, exit this iteration (wait for the next loop tick).
    4. If every task has data-status="done", the workflow is complete — write WORKFLOW COMPLETE and stop the loop.
  5. Claim it atomically (this is the critical section for two-agent safety):
    1. Set data-status="in-progress" and data-owner="<your-id>" on the chosen article. Save.
    2. git add dotnet-angular-authenticated-full-stack-workflow.html
    3. git commit -m "claim(workflow): <task-id> by <your-id>"
    4. git push origin main
    5. If the push is rejected (non-fast-forward), the other agent claimed something concurrently. git reset --hard origin/main after fetching, then restart this iteration from step 1. Do not retry the same task without re-reading.
    The push-success is the lock acquisition. Until it succeeds, you do not own the task.
  6. Execute the task per its Goal, Inputs, and Deliverable. Use the skill named in data-skill if one exists; otherwise proceed without a skill. Commit and push deliverable artifacts (code, docs, tests) as you produce them, on their own commits separate from workflow file state changes.
  7. Evaluation tasks (data-evaluation-passes > 0): run the evaluation that many times, appending findings to ./docs/evaluations/<task-id>.md before marking done. Implementation tasks use ATDD: write the acceptance test first, then make it pass.
  8. On completion:
    1. Set data-status="done" on the article and clear data-owner.
    2. Re-run step 3 so newly unblocked tasks flip to ready in the same edit.
    3. Save, then git add dotnet-angular-authenticated-full-stack-workflow.html, git commit -m "done(workflow): <task-id>", git push origin main.
    4. If push is rejected: git pull --rebase origin main, reapply your status change on top (your done still wins because you held the lock), then push again.
  9. If blocked mid-task, leave data-status="in-progress", append a note to a sibling <p data-note="blocker"> inside the article describing what is needed. Save, commit (note(workflow): <task-id> blocker), push, and exit the iteration. The other agent must not steal an in-progress task; only the owner clears it.
  10. End of iteration: ensure your working tree is clean and your local main matches origin/main. If not, you have unpushed work — push it before the loop fires again.

Concurrency rules:

  • Tasks sharing a data-parallel-group may proceed independently once dependencies are met. With two agents, the second one picks the next ready task in document order — usually the parallel sibling.
  • Only the owner of an in-progress task may modify its data-status or data-owner. Never reassign someone else's task.
  • If you find a task in-progress by another owner that has had no commits in 30 minutes (check git log -1 --format=%cI -- dotnet-angular-authenticated-full-stack-workflow.html), append a <p data-note="stale-owner"> note but do not claim it. A human will resolve.
  • Push-rejection on a workflow-file commit is the expected concurrency signal — handle it, do not panic. Push-rejection on a deliverable commit is a normal merge — pull-rebase and re-push.

Never delete tasks, reorder articles, modify data-task-id, force-push main, or change human-readable wording outside the data-* attributes and the data-note elements you append.

Attribute Legend

  • data-task-id: stable identifier referenced by data-depends-on.
  • data-status: ready | blocked | in-progress | done.
  • data-owner: unique agent identifier currently holding the task (e.g. claude@laptop-01); empty when unclaimed.
  • data-parallel-group: tasks sharing a group can run together when their dependencies are met.
  • data-depends-on: comma-separated task IDs that must be done before this task starts.
  • data-skill: the Claude skill to invoke for this task (or empty for none).
  • data-evaluation-passes: required number of evaluation iterations (0 = not an evaluation task).

Implementation Guidance (mandatory for every backend / frontend task)

This section is the only technology specification the agent will receive. Every implementation task (MB1, MF1, BP1, BT1, BI1, FP1, FT1, FI1) and every implementation evaluation (MB2, MF2, BP2, BT2, FP2, FT2, plus the per-slice eval inside BI1/FI1) MUST be executed against and verified against these rules. References below to "the guidance" mean this section.

General

  • Mobile-first web app that also looks great and works well on large screens.
  • The entire solution shall follow S.O.L.I.D. principles.
  • Implementation is radically simple: the smallest design that fully implements the requirements. No speculative abstractions, no half-built features, no dead code paths.
  • No stubs, no TODO placeholders, no throw new NotImplementedException, no console.log("TODO"), no commented-out logic left "for later". Within reason: optional integrations explicitly deferred in ./docs/idea.md or the requirements (for example, transactional email sending) may be replaced by a clearly-named no-op service that logs the intended action; this is the only acceptable form of deferred work and must be called out in the deliverable notes.
  • Every requirement listed in the approved requirements document must be implemented in its entirety before its task is marked done.

Backend (.NET)

  • Clean Architecture (Api / Application / Domain / Infrastructure separation).
  • Command/Query Separation (CQS) using MediatR (free version). Commands and queries live in the Application layer.
  • ASP.NET Core Controllers for HTTP endpoints (no minimal APIs unless the requirement explicitly demands it).
  • Entity Framework Core DbContext for data access.
  • Command and query handlers depend on an IAppDbContext interface. The concrete AppDbContext inherits DbContext and implements IAppDbContext. Replace App with the solution-specific name.
  • Do not add repository or unit-of-work abstractions over EF Core. Handlers use IAppDbContext directly.
  • Microsoft SQL Server as the database.
  • Use Microsoft.Extensions.* for Logging, Configuration, and Dependency Injection.
  • Old-style solution file format (.sln):
    • backend/src — Api project, Application, Domain, Infrastructure, etc.
    • backend/tests — backend tests.
  • One type per C# file. Every class, interface, enum, record, struct, and delegate gets its own file. NO files containing a class AND an interface, multiple enums, multiple classes, or any combination. The file name MUST match the type name (e.g., FooService.cs contains FooService and nothing else).

Validation

  • Use FluentValidation. Do not use System.ComponentModel.DataAnnotations attributes on commands, queries, or request DTOs.
  • One AbstractValidator<TCommand> per command, colocated with the command in the Application layer (<CommandName>Validator.cs). Same pattern for nested DTOs.
  • A MediatR pipeline behavior runs validators before the handler; failures throw ValidationException and the API maps them to HTTP 400 ValidationProblemDetails.
  • Register validators by assembly scanning so new ones are picked up automatically.
  • HTTP request DTOs are pure transport shapes — no validation attributes; map to commands and let the Application layer validate.

Authentication & User Management

  • Two supported sign-in flows, configurable per environment, both producing an equivalent authenticated session:
    • PKCE-based OAuth 2.0 / OIDC authorization code flow against an external identity provider.
    • Local username + password sign-in: backend validates credentials against the application database and issues a signed JWT access token (and a refresh token where appropriate).
  • Passwords stored only as salted hashes from a modern password-hashing function (Argon2id, PBKDF2 with adequate iterations, or bcrypt with adequate cost). Never store or log plaintext passwords, code verifiers, or tokens.
  • JWTs validated on every request: issuer, audience, signature, expiration. Invalid/expired tokens → HTTP 401.
  • Repeated failed sign-ins are rate-limited, locked out, or otherwise throttled, with a security audit log entry on each event.
  • Full user management — registration, sign-in, sign-out, password reset, profile management, account deletion.
  • RBAC implementation from database to frontend.

Frontend (Angular)

  • Angular Material components for every component — buttons, headers, inputs, etc. Visual language is Material 3 (https://m3.material.io/).
  • Design tokens for consistent colors and spacing across the app.
  • BEM naming convention for all HTML/CSS classes.
  • One type per file. All components MUST be split into .html, .scss, .ts file triples. NO single-file components.
  • Angular workspace split into libraries and apps.
  • Libraries use interface-driven service consumption (see https://github.com/QuinntyneBrown/interface-driven-service-consumption).

Library Structure

  • api library — models and services needed to communicate with the backend.
    • Exposes an interface for each service:
      • foo.service.ts
      • foo.service.contract.ts — includes the TypeScript interface and the injection token.
  • components library — reusable UI components (buttons, headers, etc.). Does not depend on api library.
  • domain library — UI components that depend on api library.
    • Exposes an interface for each service (if any):
      • foo.service.ts
      • foo.service.contract.ts — includes the TypeScript interface and the injection token.
  • main application — depends on api, components, and domain libraries.

Testing

  • E2E testing using Playwright Page Object Model for important functionality. ATDD: write the Playwright POM acceptance test first, then implement until it passes.

Implementation Evaluation Rubric (use for every implementation eval task)

Every implementation evaluation (MB2, MF2, BP2, BT2, FP2, FT2, and the per-slice eval inside BI1 and FI1) MUST verify each of the following and record findings under ./docs/evaluations/<task-id>.md. Any failure is blocking — fix it in the implementation, then re-run the evaluation pass.

  1. Guidance adherence. Open the changed code and confirm each relevant bullet from the sections above is satisfied. Backend evals check the Backend, Validation, Auth, and General sections; frontend evals check the Frontend, Library Structure, Auth (frontend side), and General sections; both check Testing.
  2. Requirements coverage in entirety. Every requirement in scope for this task is fully implemented end to end (UI → API → DB where applicable). No "partial" features.
  3. Radically simple. No speculative abstractions, no extra layers, no dead code, no commented-out experiments, no unused parameters, no premature interfaces, no defensive guards for impossible states.
  4. No temp code or stubs. Grep for TODO, FIXME, XXX, HACK, NotImplementedException, throw new Error("not implemented"), empty method bodies that should do work, returned hard-coded sentinel values, commented-out blocks. Each hit is a finding unless it is an explicitly-deferred optional integration documented in the deliverable notes (e.g., transactional email — replaced by a logging no-op service named accordingly).
  5. One type per file. No combined-type C# files; no single-file Angular components.
  6. SOLID + CQS shape. Backend: handlers depend on IAppDbContext, FluentValidation present for every command, no repository/unit-of-work classes. Frontend: services are interface-driven via *.service.contract.ts, libraries respect the dependency direction (components → nothing; domain → api; app → all).
  7. ATDD evidence. Acceptance test exists and was written before the implementation (check git history if needed). It currently passes against the actual implementation.
  8. Mobile-first + responsive. Frontend changes look correct at 360 / 768 / 1440 widths.
  9. Build and run clean. dotnet build and ng build (or equivalent) produce zero errors and zero new warnings. App starts from the documented run command.

Fix-on-find rule: if any evaluation pass surfaces a finding, the same agent fixes it in the implementation, commits and pushes the fix, then runs another evaluation pass. The eval task is not done until a complete pass produces zero findings.

Task Board

D1 - Create HTML mocks

Goal: Produce static HTML mocks of the core product flows from ./docs/idea.md. Mocks are visual previews only — no real backend, no live data, no JavaScript behavior beyond what is needed for navigation between mock pages.

Inputs: ./docs/idea.md

Deliverable: HTML mock files committed under ./mocks/, one file per screen, plus an index.html linking to all of them.

Mandatory design rules (the agent must follow every bullet — this section is the only design spec available):

  • Google Material 3. Every screen adheres to Material 3 design guidelines (https://m3.material.io/). Use Material 3 color roles, type scale, elevation, shape, spacing, and component anatomy. Pull the Material Web components CDN (https://esm.run/@material/web/all.js) or hand-roll markup that matches Material 3 component specs — either is acceptable as long as the visual result reads as Material 3.
  • Static, hard-coded data. Every list, table, card, form value, user name, avatar, count, date, and chart point is hard-coded directly in the HTML. No fetch, no XMLHttpRequest, no API calls, no JSON loading, no localStorage. If the screen shows "5 messages", the literal markup contains five message rows.
  • Mobile-first responsive. Author for the smallest viewport first, then add breakpoints up to tablet and desktop. Every screen must look great and remain usable at 360px, 768px, and 1440px widths.
  • BEM CSS naming. All class names follow Block__Element--Modifier (e.g., card, card__title, card--elevated). No utility-class frameworks (no Tailwind, no Bootstrap utility classes).
  • Authenticated app shell. Because the eventual product is authenticated, mock both the unauthenticated surfaces (sign-in, sign-up, password reset) and the authenticated surfaces (app shell with navigation, profile menu, sign-out). Show realistic placeholder data for a signed-in user.
  • Coverage. Mock at least: sign-in, sign-up, password reset, primary authenticated landing page, one detail/CRUD screen per primary entity from the idea, profile/settings, and an empty-state + error-state example. Add screens as the idea requires.
  • No build step. Each mock file opens directly in a browser via file:// with no bundler, no preprocessor, no npm install. Inline or CDN-link CSS only.
  • Self-contained. Mocks live entirely in ./mocks/. They do not import from the (not-yet-existing) Angular workspace and do not affect any backend project.

Done when: every screen above exists in ./mocks/, opens cleanly in a browser, renders as Material 3, looks correct at 360 / 768 / 1440 widths, and contains only hard-coded data.

D2 - Evaluate HTML mocks

Goal: Review every mock from D1 against the criteria below. Fix any failure in the mock files, then re-run the evaluation. Repeat until every criterion passes for every screen.

Inputs: D1 outputs (./mocks/), ./docs/idea.md

Deliverable: revised, accepted mocks; evaluation notes appended to ./docs/evaluations/D2.md with one section per pass listing checks performed, failures found, and fixes applied.

Evaluation criteria (every screen must pass every check; this is the entire D2 rubric):

  1. Material 3 adherence. Every page visibly applies Material 3 — color roles (primary / secondary / surface / on-surface), type scale (display, headline, title, body, label), elevation tiers, shape scale (rounded corners), and component anatomy (FAB, app bar, navigation rail/bar, cards, chips, dialogs, snackbars). A page that looks like generic Bootstrap or unstyled HTML fails.
  2. Radically simple. The design implements the idea with the smallest set of components and screens that still gives a great user experience. No speculative features, no decorative chrome, no unused navigation entries. If a screen, control, or section does not directly serve the idea, remove it.
  3. Great user experience. Primary action on each screen is obvious, reachable in one tap on mobile, and visually dominant. Secondary actions are present but de-emphasized. Empty states, loading states (static skeleton is fine), and error states are mocked where the flow can encounter them.
  4. Responsive. Open each mock at 360px (mobile), 768px (tablet), and 1440px (desktop) viewport widths. Layout must reflow appropriately at each — navigation collapses to a bottom bar or drawer on mobile, content reflows from multi-column to single-column, no horizontal scroll, no clipped content, no overlapping elements.
  5. Static + hard-coded. View source or grep — confirm there is no fetch(, no XMLHttpRequest, no localStorage, no sessionStorage, no JSON file loading. All displayed data is literal in the markup.
  6. BEM naming. Class names follow Block__Element--Modifier. No utility-only classes from Tailwind/Bootstrap.
  7. Coverage vs. idea. Every primary user goal expressed in ./docs/idea.md has at least one mocked screen. Every primary entity has at least a list and a detail/edit view mocked. Sign-in, sign-up, password reset, profile, and sign-out are present.
  8. Mobile-first appearance. The mobile layout is not just a squished desktop — controls are touch-sized (≥48dp), spacing is comfortable, type is legible.
  9. No build step. Each .html file opens via file:// with full styling and navigation working. No console errors.

Per-pass loop (one full pass = required by data-evaluation-passes="1"; run additional passes if the first finds failures):

  1. Open each mock in a browser at 360 / 768 / 1440 widths. Note failures per criterion in ./docs/evaluations/D2.md under a ## Pass N - findings heading.
  2. Fix every failure in the mock files.
  3. If any fix was applied, run another pass. Stop only when a full pass produces zero findings.

Done when: a full evaluation pass produces zero blocking findings across every screen and every criterion, and the final clean pass is recorded in ./docs/evaluations/D2.md.

Done when: tasks cover the entire plan, each is small enough to finish (implement + eval) in a small number of loop iterations, and no task crosses library boundaries inconsistently with the guidance.

FT2 - Evaluate frontend tasks

Goal: Verify the FT1 task list against the approved plan and the Frontend, Library Structure, Authentication (frontend side), Testing, and General sections of Implementation Guidance. Fix-on-find: amend the task list, re-evaluate. Findings under ./docs/evaluations/FT2.md.

Inputs: FT1 outputs, approved frontend plan, accepted mocks

Deliverable: approved frontend task list.

Explicit checks: every task is a true vertical UI slice; no "scaffolding only" tasks; library boundaries are respected (a task in components never imports from api); every task names its Playwright POM acceptance test; every task names which guidance rules it must satisfy; sizing is small enough that one task = a few loop iterations.

Done when: a full evaluation pass produces zero blocking findings.

FI1 - Implement each frontend task with ATDD (Playwright POM)

Goal: For every approved frontend task: write the Playwright POM acceptance test first (ATDD), implement against the Frontend, Library Structure, Authentication (frontend side), Testing, and General sections of Implementation Guidance until the test is green, evaluate the implementation against the Implementation Evaluation Rubric, fix any finding, then move on.

Inputs: approved frontend task list, accepted frontend MVP, accepted mocks

Deliverable: per slice: passing Playwright POM acceptance test; route + components in the right libraries; service in api with its *.service.contract.ts; Material 3 visual fidelity to the corresponding mock; per-file split (.html/.scss/.ts); BEM CSS; design tokens used; mobile-first responsive; no stubs. Evaluation note appended to ./docs/evaluations/FI1-<slice-id>.md.

Per-slice loop:

  1. Write Playwright POM acceptance test for the slice. Commit + push.
  2. Implement until the test passes, following every applicable guidance rule. Commit + push.
  3. Run the Implementation Evaluation Rubric scoped to frontend. If any finding, fix in the implementation, commit + push, re-evaluate. Repeat until a clean pass.
  4. Verify the slice visually matches the mock at 360 / 768 / 1440 widths.
  5. Mark the slice done in ./docs/plans/frontend-tasks.md. Commit + push.

No stubs. A slice is not done if it contains TODO, debug console.log, empty methods, hard-coded fake responses, single-file components, inline templates, or any deviation from BEM / per-file / library-direction rules. Only explicitly-deferred optional integrations may be replaced by a logging no-op service named accordingly and noted in the evaluation file.

Done when: every frontend task is implemented, has a passing Playwright POM test, has a clean evaluation pass on the rubric, visually matches its mock, and is marked done in the task list.

DP1 - Create Azure deployment workflow (cheapest plan)

Goal: Add a Git workflow that deploys the app to Azure on the cheapest viable plan, provisioned via the Azure CLI.

Inputs: implemented backend and frontend

Deliverable: CI/CD workflow file, Azure CLI provisioning script, and deployment docs.

Done when: a push to the deploy branch provisions and deploys successfully.

TP1 - Create test plan

Goal: Author a test plan covering happy paths, edge cases, and regressions.

Inputs: requirements, implemented app

Deliverable: test plan document in the repo.

Done when: all requirements have at least one test scenario.

TP2 - Ensure app runs locally

Goal: Verify backend and frontend start cleanly on a fresh checkout.

Inputs: repo

Deliverable: documented local run command and a green smoke check.

Done when: a fresh clone runs the app from a single command.

TP3 - Run test plan 5 times, log bugs, fix bugs

Goal: Execute the test plan five times. Each pass: log bugs to a markdown file in ./docs/bugs/, then fix them before the next pass.

Inputs: test plan, running app

Deliverable: 5 dated bug logs under ./docs/bugs/ and fixes merged for each.

Per-pass loop: run plan -> append bugs to ./docs/bugs/pass-N.md -> fix -> rerun until pass N is clean -> proceed to pass N+1.

Done when: pass 5 finishes with no new blocking bugs.

Parallelism Map

  • mvp-backend (MB1, MB2) runs in parallel with mvp-frontend (MF1, MF2) once R2 is done.
  • backend-impl (BP1 -> BP2 -> BT1 -> BT2 -> BI1) runs in parallel with frontend-impl (FP1 -> FP2 -> FT1 -> FT2 -> FI1).
  • Within each implementation track, BI1 and FI1 iterate per task: implement (ATDD) -> evaluate -> next.
  • Deployment (DP1) waits for both BI1 and FI1.

Decision Log

  • Evaluation gates follow every produced artifact (mocks, requirements, MVPs, plans, task lists, implementations).
  • ATDD is mandatory for implementation tasks; Playwright Page Object Model is mandatory for frontend tasks.
  • MVPs exist to lock in patterns before scaling implementation.
  • Vertically sliced tasks are the unit of progress during implementation.
  • Azure deployment uses the cheapest viable plan provisioned via Azure CLI.
  • Test plan executes 5 full passes, with bugs tracked per-pass under ./docs/bugs/.
